# 后续处理事项

记录实施过程中新增的缺陷、改进、后续功能和待决策问题。一项一文件，保存在[本目录](.)，以文件内的稳定 ID 引用；此页只维护规则，不手工复制全量清单。事项被记录或合入主线，不代表批准实施或承诺排期。

既有里程碑能力仍由 [v2.0 设计](../../requirements/v2.0/01_design_v2.0.md) 和 [当前实施记录](../0.1.0/README.md) 跟踪。功能文档描述当前行为和兼容边界；实施记录保存当时的结果与证据，通过链接关联事项，不另维护一份待办状态。

## 查看与跨分支协作

- 日常开发先查看当前工作区中与任务有关的事项，再按需比较本地目标分支；不用每次扫描所有分支。
- 阶段规划时显式选择参与开发的分支，运行只读汇总：

  ```sh
  npm run followups
  npm run followups -- --refs main codex/0.1.0-markdown-compat codex/0.1.0-pdf
  ```

  默认查看 HEAD；命令读取本地 Git 提交快照，不包含未提交修改，不 fetch、不切换分支、不修改记录。远程跟踪分支也只是最后一次 fetch 的本地快照。输出保留每个分支的状态与实施引用，提示缺项和内容差异；不按时间或最先进状态自动合并。旧版单文件条目会提示人工迁移，不假装已纳入汇总。未采用新结构的分支显示无独立记录，不表示没有待办。
- 新事项随发现它的分支提交。记录来源分支及可定位的已有提交；分支名是工作线索，提交是稳定依据。不要为了记录自身提交而反复修改提交哈希。
- 开始处理前查重、核对实施分支／PR，在同一事项中记录认领范围。Git 文件不能提供实时跨分支认领锁；存在重叠工作时先协调，不能仅凭本地未见记录就认定无人处理。
- 合并时核对重复事项和状态分歧。相同事项保留一个 ID；重复文件保留并标记“重复”，链接保留项，不删除历史引用。不静默覆盖另一分支的证据。
- 废弃或删除开发分支前，把仍有价值的未完成事项通过单独文档变更带入目标分支；不要把发现留在即将消失的分支。

## 文件与状态约定

文件名为稳定的英文语义 ID（小写字母、数字、连字符），如 `quarto-qmd-support.md`；不使用需要跨分支分配的流水号。标题可修改，ID 不随标题、版本、状态变化。历史编号可作为旧引用保留，但不再分配。新增事项先按现象、模块和 ID 查重。

状态只选一个：**待评估、已安排、处理中、已解决、暂缓、无需处理、重复**。

- 待评估：尚需决定是否处理；暂缓：说明暂不处理原因及重新评估条件。
- 已安排：已有明确阶段或工作安排；处理中：已经开始实施。
- 分支上验证通过但尚未合入目标分支，仍为“处理中”，在验证证据中写明“待合入”。满足验收且合入目标分支后才标记“已解决”，附合入与验证依据；可在后续整理提交中关闭事项。
- 只完成部分范围时保留未完成验收项，不整体关闭。发现回归时重新打开并追加依据。
- 无需处理必须说明决定和原因；重复必须链接保留项。记录的状态不替代对目标分支代码的核对。

## 事项模板

前三项使用下面固定的字段名、ASCII 冒号和单行值，供汇总命令读取；正文按问题复杂程度填写，尚未确定的信息明确写“待决定”，不编造优先级或排期。

```md
# 事项标题

- ID: stable-topic-id
- 状态: 待评估
- 实施分支／PR: 未安排
- 类型: 缺陷／改进／后续功能／待决策（选一）
- 发现依据: 日期、来源分支、已有提交或文档链接；区分观察结果和推测
- 目标分支: main（或实际目标）

## 问题与影响

现象、复现或证据、适用范围及影响。

## 处理条件与范围

暂不处理原因、重新评估触发条件、建议范围和开始前待决策问题。

## 验收条件

可观察的完成条件；部分完成时保留未完成项。

## 处理记录

日期、决定依据、实施与验证链接、待合入或合入情况。无需处理写原因；重复写保留项链接。
```

当前任务必需的修复不能通过登记事项绕过验收。范围外的发现按此规则记录，在任务结束时汇报 ID；不自动扩展当前实现范围。Agent 操作要求见 [AGENTS.md](../../../AGENTS.md#follow-up-tracking)。
