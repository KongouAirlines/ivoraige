# 0.1.0 标识符下划线分行候选

最初候选分支 `fix/0.1.x-pdf-underscore-line` 基于 #80 的 `c273d36`，当时不包含 #73/#74 模型边界或 #79 工作台选择修复；这是历史验证基线，后续同步见下文。

## 原创复现与原始v1窄规则

实际 BabelDOC 0.6.4 分行方法对原创字形 `X_Y`（字母同一基线、下划线视觉范围较低）生成 `[X,Y]`、`[_]` 两行，后续分组沿用该顺序。候选只为满足下列条件的 `_` 采用相邻字母的有效 y 范围参与原分行算法：

- 原 composition 中连续三个字符；两侧均为单个 ASCII 拉丁字母，不跨非字符结构。
- 三者横排、同一个明确 XObject、字体和完全相同的正有限字号，字框与有效范围有限且非退化。
- 横向位置递增，邻接间隙在 -0.15em 至 0.5em 内；左右字母有效中心高度差不超过 0.1em。
- 下划线中心至少低 0.2em、最多低 1em。更远的低位符号不拉回正文。

只改变这次分行计算的临时范围，不改字符、坐标、字体、render order，不全局排序。条件不满足时调用原方法；正常退出和异常均恢复实例/类方法。该规则是明确范围的兼容适配，不是通用阅读顺序算法，也不能保证所有公式或标识符。

## 捕获与回放

新捕获现固定 `captureConfig.underscoreLinePolicy: ascii-base-v2`；已保存v1继续原规则，缺少标记的旧绑定继续原引擎方法。捕获和冻结回放按保存标记选择，不自动修改历史绑定，需重新导入才能启用新策略。它与 `layoutFitPolicy` 独立，旧/v1/v2组合均可回放，未知策略在引擎启动前拒绝。协议与绑定 schema 不变。独立 PDF 组件源码同时携带适配模块，仍须完整重建。

## v2：以名义框判断基线

BabelDOC前端从LTChar bbox保留名义框，再单独调整字形visual bbox；不同字母的墨迹中心不必相等。只扩大v1的视觉中心阈值不能区分正常字形高度差和真实基线错位。

v2保留原有ASCII字母邻接、同样式、XObject、方向、距离、低位与有限几何条件，但基线条件改为三者名义框的上下沿分别在0.05em内一致，且左右墨迹范围有纵向重叠。没有名义框、名义基线错位或墨迹不相交时不修正；仍只借用左右字母的有效分行高度，不改坐标或全局排序。

原创12pt字形正例使用同基线名义框、左右3pt和6pt墨迹高度（中心差1.5pt）：v1拒绝，v2恢复同一行。锁定引擎专项5/5、快速测试33/33，覆盖v1行为保留、错位/无效名义框、视觉分离、多行、上下标、RTL及原负例。该例不是私人样本的复刻，也不是实机验收。本地已按普通merge包含#77的setext修复，组合npm test（含构建）547通过、2跳过、0失败；继承布局专项3/3、归档审计4/4、npm包smoke（83文件）通过。这里是本地验证，发布状态以实际PR head为准，不能用这些结果指代未更新的远端。
