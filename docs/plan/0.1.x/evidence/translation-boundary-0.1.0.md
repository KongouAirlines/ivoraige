# 0.1.0 translation target boundary, stage 2A

Related: [issue #59](https://github.com/KongouAirlines/ivoraige/issues/59). This stage changes the default translation request instruction only. The request still sends `sourceLang`, `targetLang`, `effectiveContext`, `effectiveTarget`, and `sourceText` as JSON through the existing DSH LLM service. The instruction now identifies `sourceText` as the sole target, limits `effectiveContext.before/after` to disambiguation, treats request values as data, and excludes the request wrapper and neighboring text from the answer. JSON occurring within `sourceText` remains a valid target. The prompt identity changes from `scientific-translation-v2` to `scientific-translation-v3` on newly generated model revisions. Stored records, wire shape, placeholders, term preflight, and applicability-based reuse remain unchanged.

Local verification: the pinned DSH source was bundled with Node 24.22.1. `node --test test/translation-model.test.mjs` passed 10/10, including short-label/neighbor request inspection, JSON source text, credential isolation, stream completion, and an end-to-end accepted MD/JSON export and restart reuse test. `npm test` built the DSH and web bundles and passed 538 tests, with 2 skipped and 0 failed. The model requests use a mock HTTP stream, not a real translation model; the tests prove request shape and local response handling, not model obedience.

Remaining issue #59 acceptance: run an authorized real-model short-label and neighboring-paragraph case, inspect the accepted revision and PDF/MD/JSON from one frozen snapshot, and confirm no wrapper or extra neighbor text. Add local candidate handling for a recognizable bad wrapper with #57 semantics before closing the issue. Existing polluted accepted revisions and their frozen snapshots are not repaired by this prompt change and can still be reused under unchanged applicability; review and replace them explicitly.
