## 插件包与安装

建议先同仓维护、独立构建/分发，仓库拆分后议。官方目录首轮只允许明确来源的包；声明 hostApiRange、pluginVersion、所需服务/能力、binding/schema/sidecar 协议兼容、OS/架构、runtime/资源和配置版本。外部引擎版本独立锁定并保存来源；宿主 `0.1.x` 不要求插件也叫同一版本。

P05 是 DSH AppBoot/Loader 上的包交付薄层：沿用它们的配置与 Cordis 装配/生命周期；ivoraige 只补受控目录、兼容检查、暂存和安装恢复事务，不另造 DI、Loader 或服务注册框架。DSH 当前 eager/non-transactional 行为不自动提供该事务，失败时由交付层恢复包清单，再由既有装配链重启。

安装流程为下载/本地导入 → 校验来源清单与摘要 → 检查兼容/依赖 → 暂存 → 完整性检查 → 原子登记 → pending-restart → 重启激活。失败只清理本次拥有的暂存；保留上一完整版本及诊断。无关业务不停止。运行任务占用插件时不得删除文件；卸载、禁用、清除缓存、删除用户数据是不同动作。恢复入口可列包、查看诊断、回退清单、禁用故障项；不要求 WebUI 完整启动。

摘要用于发行/下载完整性，不扩展为日常文档传递反复全量 hash。首轮不承诺第三方插件安全沙箱、自动更新、市场、任意热卸载或跨平台统一原生包。

## PDF 依赖与分发边界

现有许可选择见 [LICENSE](../../../LICENSE)、[THIRD_PARTY](../../../THIRD_PARTY.md)。本计划遵循已有选择，不另作许可证决策。BabelDOC Python 插件虽已声明独立 AGPL 分发，**实际依赖和最终包拆分仍需证明**；进程分离、源码目录移动或声明文本都不能代替实际归档清单。

P08 必须逐项核对：

1. 主体的 direct/transitive 依赖、构建 bundle、npm tarball、独立运行时包和安装目录都不夹带应归独立 PDF 插件的 AGPL 代码/库/资源，也不能由主体启动时隐式下载。主体适配代码如需保留，明确许可证及依赖边界。
2. 独立 BabelDOC 包承载其完整实际闭包：已知关注 BabelDOC 0.6.4、PyMuPDF 1.26.7/MuPDF、随包 native DLL/PYD、PyInstaller 内嵌代码、字体/模型资源；其他传递依赖按各自许可查证，不一律称作 AGPL。
3. 对照 [历史实际包审计](../0.1.0/pdf-license-audit.md) 的包、原生、资产三份映射，补齐适用许可/版权/NOTICE、对应源码及构建安装材料的获取关系。FFmpeg、setuptools、字体/模型等不能只看顶层 requirements.lock；旧报告记录是排查入口，不是新包验收结果。
4. 禁止把 PyMuPDF 暴露成主体或其他 PDF 插件的公共工具。新 PDF 能力独立选择非 AGPL 依赖或明确自己的分发边界；MinerU 包同样核验实际代码、模型、字体及资源许可，不借用 BabelDOC 的结论。
5. 每个实际发行包记录文件名、字节数、摘要、构建源码提交、构建 run/工具链、插件及引擎版本、文档/通知/源码入口。脱离 `.git` 的源码归档、未装 PDF 的主体安装、插件安装后冻结回放都需实测。

恢复相应 Windows/PDF 二进制分发前完成 F-B/P2 对应的实际包验证；纯 Node 包须通过自身实际闭包/许可与安装门禁，不因旧 PDF 附件的问题一概停止，也不因不带 Python 自动视为合规。npm 准备见[就绪清单](../0.1.0/npm-readiness.md)，本轮不安排上架。旧附件撤下停止继续下载，不代表旧包已修。不得主动恢复历史 tag/附件，或把文档计划写成已经发布。源码开源、仓库边界、包分发边界分别决策，P08 不以全面重写或更换 PyMuPDF 为默认前提。
