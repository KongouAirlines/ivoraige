# M0–M3 总结与后续实施原则

日期：2026-09-30。依据用户在 M3 完成后的方向调整，以及当前代码和阶段记录。本文件用于后续规划；不追改历史实验结果，也不表示以下改进已经实现。

## 1. 当前成果的准确定位

M0 建立了可复用材料，M1 验证 DSH 与 BabelDOC 接入，M2 建立文本修订／术语／多出口业务闭环，M3 在 R03 第 1／2／4 页验证接受修订驱动 PDF／Markdown／JSON、零正文模型重导出及失败／取消处理。**M3 证明可行性与记录复用，不证明自动解析修复、任意 PDF 排版或无需干预的翻译质量。**

M3 的 47 次本地正文调用中，25 个草稿通过结构检查、22 个因占位符问题被拒收；随后由代理核对原文并修订接受。通过结构检查也不等于语义正确。最终页面质量包含代理修订与样本专用处理的贡献，不能归为通用算法的自动成功率。历史“未经用户专业签认”只是来源说明，**不再作为进入后续阶段或日常导出的默认前置**。

## 2. 审阅不是默认流程：区分版本选定、结构校验与语义审校

目前 `src/task.mjs` 的模型审校 `review` 默认关闭；但是模型结果保存为 draft，导出要求存在 accepted revision。M3 的接受脚本由代理逐项修订后调用 accept。因此当前软件仍需要显式选定译文版本，尚未实现自动接受策略；“已经不强制二次模型审校”不等于“已经全自动”。

后续保留接受修订作为**输出版本的选择记录**，不要把它等同人工逐条审阅。普通任务优先采用“翻译一次 → 算法检查 → 按配置自动选定可用版本 → 导出”；检查和选定策略可独立替换。只对实际异常进入修复或复核，用户主动选择的精翻／审校方案仍可保留。现有库结构本轮不改，未来实现策略时记录 `automatic`、`agent` 或 `human` 来源，不能假称自动检查证明科学语义正确。

优先用算法处理来源绑定、占位符完整性、单位／修订一致性、文本保留及已知版面约束。跨页断句等困难情况，可先用阅读顺序、段落位置、标点等规则筛选候选，再按需调用 LLM 判断合并或对齐关系；只处理疑难局部，结果保存一次并复用，不默认全文重审。仍无法确定时，仅把具体疑点交给用户。跨页方法尚未实现或验证，不能把所有跨页内容自动合并。

## 3. 质量边界：中间层不额外降质，不替上游无限修复

用户要求的默认目标是忠实承接所选解析／翻译／排版工具的能力。对同样输入与配置，ivoraige 不应新增丢段、改义、损坏符号、错误映射或重复模型调用；不以精修出版级页面作为每个任务的默认交付条件。

| 问题归属 | 当前例子与证据 | 后续处理 |
|---|---|---|
| 上游输入／解析缺陷 | M1 的 `We` 被拆为独立段并由长度阈值跳过；R03 的邮箱尾字、断词和符号抽取错位 | 已证实属于上游的缺陷可记录后暂不修，不自动阻塞项目推进或要求人工补齐。工具已提供合适配置时优先使用配置；默认不逐篇修字 |
| 本项目映射或集成新增的问题 | 接受投影与可读输出不一致、错误位置绑定、适用性变化仍复用旧记录 | 由本项目修复；上游缺陷不能作为静默丢失或错误复用的理由 |
| 翻译模型能力／提示接口不匹配 | 小模型大量增删 `<bN>`；翻译任务中同时要求重建复杂结构 | 先简化接口，尽量由适配器保护结构、模型只翻译可译文字；上下文不要因此被无意义切碎。用小规模对照验证，必要时换模型或只修异常，不默认增加全文审校 |
| 上游排版与翻译长度共同作用 | 中文图例侵入曲线、字段标签与原矢量布局不协调 | 先比较同一上游原生路线和本项目路线，确定是否为新增回退。已知上游排版限制可保留；不能未经对照就把问题一律归给上游 |
| 原文自身的疑点 | 区域索引“0 到 256”与“256 项表”并存 | 忠实保留，可加来源注记，不自行改写科学结论，不阻塞普通翻译 |

现有 M3 没有为每一种缺陷运行同配置的完整上游原生对照，因此不能断言所有已修版面问题都由上游导致。后续仅在归因会影响实现决策时，选少量代表案例做对照；不为每份文件强制跑两遍。目视是开发验收的抽样手段，不是产品每次输出必经的人工作业。

## 4. 通用能力与样本专用处理分开

已可复用的部分包括固定依赖环境、引擎请求捕获、来源快照内位置＋原文匹配、持久修订与接受清单、占位符校验、同一修订的确定性投影、零模型回放及错误／取消拒发。

样本专用部分包括 `m3_snapshot.py` 的 R03 页码／文本分类规则、`m3_prepare_pages24.mjs` 的单位 ID 与逐项符号修正、`m3_accept_page1.mjs`／`m3_accept_pages24.mjs` 的固定材料处理，以及依据本样本确认的脚注尾字和场分量区域恢复。`adapter.py` 的重绘也含固定横坐标 74／76／77 和特定字段文字处理；虽然部分操作由清单驱动，区域确定和处理假设仍来自本样本，不能称为通用识别算法。这些补丁已混入适配执行路径，后续要显式隔离，不能仅靠文档声明它们是实验。

后续不继续以“再修好几篇”代替产品能力。实验脚本留在 `experiments/` 作为证据和回归案例，默认生产路线不依赖 R03 ID、固定页码、固定句子或手填坐标。若同类问题值得解决，提炼出可解释的规则和输入输出，再用少量不同布局验证；无法泛化且属于上游缺陷的处理暂留实验，不拉入核心。

通用性验收使用“未参与规则编写的新布局／新材料”，与现有样本上的回归结果分开记录。用少量有区分度的案例即可，不重建大规模语料或重复解析全书。

## 5. 模块化现状与目标边界

当前模型、术语、任务、存储和文本导出已按 Cordis 服务分离，导出不要求挂载模型服务。但 PDF 尚未成为独立 Cordis 服务：`src/app.mjs` 未装配 PDF 导入／渲染插件；CLI 的 `import-pdf` 直接进入 `Records.importPdfSnapshot`，记录服务知道 `<bN>`、BabelDOC 占位符和 PDF 位置。Python `adapter.py` 同时承担引擎 hook、清单校验、区域恢复、取消与 MD／JSON 写出，和 `src/export.mjs` 存在文本出口逻辑重复。

MinerU 目前提供材料准备与覆盖参考，没有作为运行时可替换解析插件接入；M3 直接使用 BabelDOC＋PyMuPDF，尚未实现 pdf2zh-next 完整流程适配。Docling 只是未来候选，本轮未调研或证明其能力。

后续采用以下逻辑边界，名称仅为设计建议，不一次拆成大量发布包：

| 层次 | 应负责 | 不应知道 |
|---|---|---|
| 通用文档／翻译记录 | 文档、可译单位、来源修订、接受版本、文字和结构的关系 | BabelDOC 类名、`<bN>` 语法、某篇论文坐标 |
| 解析接口与实现 | 产生可译内容、来源定位、阅读顺序和保留结构；报告实际能力／缺项 | 不假定解析器能重建 PDF |
| 通用 PDF 输出接口 | 消费冻结接受清单和适用的来源绑定，返回结果／诊断并响应取消 | 不指定用 MinerU、BabelDOC 或另一实现 |
| 具体工具适配 | MinerU／未来 Docling 的解析映射；BabelDOC 的捕获、占位符、hook和排版；未来 pdf2zh-next 的流程接入 | 不自行调用正文模型补译，不修改核心术语业务 |
| 任务装配 | 选择解析、翻译、输出插件并管理其生命周期 | 不将某个工具的完整应用当作所有任务的必选依赖 |

来源绑定保留带适配器标识／版本的私有信息，核心只保存和传递，不解释引擎坐标与占位符。通用结构只提炼本次已需要的字段，避免设计覆盖所有格式的巨大中间表示。

解析接口和 PDF 输出接口应分开：MinerU／Docling 的块不能假定与 BabelDOC 请求一一对应。若使用不同解析与重建引擎，建立独立的关联步骤，允许明确的多对多关系；跨页合并也保存原片段和引擎绑定，不把合并文本硬塞回单一 bbox。现阶段允许 BabelDOC 使用自身解析结果直接回填，跨引擎关联不是所有任务的必选前置。

## 6. 各阶段经验补充

- **M0：** 样本用于暴露机制差异，参考译文本身也可能有错误或多种合理表达；不能把样本修订当成产品算法。继续复用已有解析和开发／留出划分，新布局小样不应暗用留出译文调规则。
- **M1：** 接入机制可行不等于质量全过；已有实验应尽早区分上游基线和适配器新增行为。固定版本有价值，但不是承诺长期维护完整 fork。后续只重跑受升级影响的代表案例。
- **M2：** 接受版本、幂等复用、取消与模型解耦值得保留；“接受”不必绑定人工动作。语义质量不足优先定位模型、上下文、提示或术语适用性，审校是可选策略。术语分类与适用范围待库结构规划，不顺手扩大本轮范围。
- **M3：** 实际花费过多精力在已知样本的科学排版上，超出了可复用中间层验证所需。接下来优先抽离通用契约、隔离样本补丁、验证不额外降质；不继续以更多逐页修复作为主要里程碑。模型占位符失败、抽取符号乱码和版面限制应分别统计，避免用最终代理修订后的47/47掩盖自动处理效果。

## 7. 建议的后续顺序

1. 先整理已有模块边界：将引擎占位符处理和 PDF 专用校验从核心记录服务移到适配层，三个出口共用冻结清单和文本呈现逻辑，保留已有复用与取消行为。
2. 用当前 BabelDOC 实现验证薄接口，并用少量原创的另一种来源结构验证核心无需修改；真正接入第二个解析器时再补实际所需字段，不现在安装全部候选工具。
3. 增加算法检查后的自动版本选定策略，普通任务不默认二次审阅。用小样验证结构保护是否减少模型负担，不能靠手工修订来证明自动路线通过。
4. 有实际跨页／多对多案例后，再做规则优先、LLM 局部辅助的关联方法。上游固有缺陷默认作为限制记录，只解决有共性且对主流程有价值的部分。

以上是历史建议，其中模块边界与最小第二来源结构已在 M3.1 验证。**2026-09-30 用户决定跳过拟议的 M3.2，直接进入 M4 简化 CLI 和 MVP 收尾。** 自动版本选定、占位符顺序改进、第二个真实解析器与跨页关联均移入后续建议，不作为进入 M4 的条件。

## 8. M3.1 试用后的取舍

- 新论文试译已由用户验收通过。被拒收的是正文场方向段落的占位符重排，摘要实际已生成译文；不把拒收写成漏译，也不将它归因于摘要解析。证据见 [M3.1 完成记录](m3.1/completion.md)。
- 未来结构校验应区分 token 身份、次数、嵌套／关联与线性顺序，允许翻译所需的合理语序变化。需结合真实结构验证，不能直接删掉顺序检查或针对某一句绕过。这项改进本轮不实现。
- 用户认为版面逊于 pdf2zh-next。先保存[固定源码研究](../../research/pdf2zh-next-mvp-reference.md)；以后改进时从配置、段落翻译、公式／富文本保留和排版参数逐项对照，不立即再跑全文基线，也不逐页手修。
- 组件按需安装与装配同样适用于核心、UI、模型、任务、术语及存储；不同入口复用业务服务。先保留清晰边界，确有需求再独立发包，不以全面包拆分阻挡 MVP。
- M4 采用用户选定的简化 CLI、复用 JSON 配置和使用文档。沿用现有显式版本选择与导出约束；批量操作是用户选择输出版本，不等于人工审阅或已经实现自动语义验收。Web UI、词典、库结构和排版优化留后续。
