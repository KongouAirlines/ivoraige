# 0.1.0 基础体系规划

## 为什么基础先行

已有内核能导入、翻译、审校和冻结导出，但静态装配、格式与实现身份耦合、入口及安装边界会让新增能力反复修改主体。先明确 Cordis/DSH 生命周期和公共契约，才能用独立插件验证组合，同时保留 Records、修订、复用及冻结输出。

运行时基线探针与候选升级分开，数据兼容与接口接线逐步推进，使问题可以归因和回退。依赖拆分必须落到实际发行闭包，不能只移动目录。完整原生桌面与真实引擎质量则需要不同证据，分开验收更容易控制每个 PR 的范围。

## 交付目标

具体版本内容以 [releases 的 0.1.0 范围](../0.1.x/releases.md#范围与放行条件)为准；工作包和执行顺序查[执行索引](../0.1.x/work-packages.md)。本文只记录基础优先的理由。

## 放行证据

由 releases 指定的[验证 ID](../0.1.x/validation.md)与实际提交证据共同判断。运行时选择见[专项评估](../0.1.x/runtime-sequence.md)，拆包与数据保留见[迁移分发](../0.1.x/migration-distribution.md)，包身份和安装入口见[npm 就绪准备](npm-readiness.md)。

同目录的[实施记录](README.md)保留原日期及提交；当前源码版本与候选范围的关系见[版本身份](../0.1.x/releases.md#版本身份)。
