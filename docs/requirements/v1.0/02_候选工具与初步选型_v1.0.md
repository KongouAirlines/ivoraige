# 通用翻译中间层：候选工具与初步选型

版本：v1.0｜2026-09-29｜配套候选池与关注顺序，非最终选型

保留 v0.5 的 **16 个分组、83 个候选条目**（部分为相关组件组合，不等于独立产品数），按用户修改后的 v1.0 需求基线同步关注顺序。原有 **优先看** 表示同组中值得比较的对象，不代表该组已列入近期范围，也不是本轮重新评定的排名。

本轮是文档合并与优先级同步，**没有新增候选或联网核查**。各项目的能力描述、资料入口和既有判断沿用 v0.5；历史查阅范围见 [sources.v1.0.md](sources.v1.0.md)。功能与当前优先级见 [01_功能需求概览_v1.0.md](01_功能需求概览_v1.0.md)，本表不单独决定需求优先级。

开源优先，也保留可接入的闭源软件和商业服务。接入方式仍区分：直接调用后端、让现成客户端调用本项目、复用组件或参考流程；提供接口不代表已完成适配。

## 与 v1.0 基线对应的关注顺序

|---|---|---|---|

| **P3：多人协作** | F-43 | 需要时再比较交接工具或协作平台。 | 简单文件交换可先用现成工具；不将实时多人或账户平台作为近期依赖。 |

方案保存、小样试译、翻译记忆、解析校正、原生 LaTeX 和双语输出，继续在现有候选中寻找复用点。本版不重做工具调研，也不据通用格式支持推断其已经完整支持 LaTeX 工程往返。

## 一、基础需求相关

### 1.1 插件载体

对应 F-01。关注功能插件怎样组合与替换；对外 MCP／OpenAI 入口另列第 3.8 节。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看 · [Cordis](https://github.com/cordiverse/cordis)**<br>开源框架 | 插件／服务接口 | 适合组织插件依赖和生命周期，是当前优先考虑的项目载体。 它不是现成翻译系统，功能仍由本项目与插件提供。 |

初步关注：继续将 Cordis 作为优先考虑的插件载体，不在本轮确定其内部服务划分。

### 1.2 本地推理与资源运行

对应 F-04、F-27、F-34。F-27 的已有服务兼容 API 接入在 P0，运行管理在 P1；F-04 按需运行在 P1，F-34 的流程预热优化仍在 P2。

运行器和模型分开选择；用户已有部署可以直接作为候选，不要求随项目安装全部环境。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看 · [Ollama](https://docs.ollama.com/api/openai-compatibility)**<br>开源运行器 | HTTP／兼容接口 | 支持空请求预加载，以 keep_alive／stop 控制驻留或释放；原生生成响应提供 load_duration。适合复用底层能力实现流程预热，何时加载仍由本项目或用户配置决定。 |
| **优先看 · [LM Studio](https://lmstudio.ai/docs/developer)**<br>桌面软件／开放 API | 兼容 API／原生接口 | 兼有图形界面和原生加载／卸载接口；支持 JIT、空闲 TTL 与 Auto-Evict，加载响应提供 load_time_seconds。适合作为预热和释放的直接接入对象；使用时协调其自身释放设置。 |
| **优先看 · [llama.cpp / llama-server](https://github.com/ggml-org/llama.cpp)**<br>开源推理工具 | 进程／HTTP | 量化模型和小型自管服务的直接路线；现有空闲休眠与新任务唤醒能力可复用。流程提前唤醒仍需连接逻辑，模型架构、模板与运行参数需要匹配。 |
| [vLLM](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/)<br>开源推理服务 | 兼容 API | 适合服务器和批量推理路线，可复用已有模型服务。 个人低资源设备不必首先引入完整服务栈。 |
| [Xinference](https://github.com/xorbitsai/inference)<br>开源模型服务 | HTTP／客户端库 | 可集中部署和管理多类模型，便于同时接翻译、嵌入等能力。 当只使用一个本地模型时，额外管理层可能没有必要。 |

初步关注：第一批优先接 Ollama 和 LM Studio；更轻的自管服务考虑 llama.cpp，服务端批量需求再比较 vLLM 或 Xinference。

**对应 F-34：优先复用运行器的加载／释放能力，补一层流程时机判断。**“空闲后卸载”与“提前知道下一步要用谁”是两种能力；后者结合翻译链和任务进度，决定预热、暂时保留或释放，不必使用另一个 LLM 做资源调度。

Ollama 的 [FAQ](https://docs.ollama.com/faq) 已说明空请求预加载和驻留控制，[原生生成接口](https://docs.ollama.com/api/generate) 提供 `load_duration`；LM Studio 的 [加载接口](https://lmstudio.ai/docs/developer/rest/load) 提供 `load_time_seconds`，另有 [卸载](https://lmstudio.ai/docs/developer/rest/unload)及 [TTL／Auto-Evict](https://lmstudio.ai/docs/developer/core/ttl-and-auto-evict)。llama-server 的 [服务文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) 记录空闲休眠和唤醒。

上述耗时通常是加载后的实际记录，不是对下一次启动的预报。建议作为历史参考，结合当前阶段剩余时间、模型是否已驻留及可用内存／显存决定提前量；没有接口耗时时可自行记录就绪耗时。资源不足时顺序交接；后面很快仍需使用的模型可暂留，不追求每段翻完立刻卸载。这里只明确目标，暂不固定算法、阈值或接口字段。

## 二、翻译核心相关

### 2.1 翻译模型与商业翻译服务

对应 F-02、F-05、F-11、F-12。

这里列适合加入模型池的代表，不预先决定某个模型负责所有语言和文体。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看 · [腾讯 HY-MT 系列](https://github.com/Tencent-Hunyuan/Hy-MT)**<br>开放权重／按模型许可 | 本地推理／模型适配 | 翻译专用模型，可作为强模型建设之后的大量正文执行候选。 术语约束、文体和目标设备表现仍需样本比较。 |
| **优先看 · [Qwen-MT](https://www.alibabacloud.com/help/en/model-studio/machine-translation)**<br>商业云 API | 模型 API | 提供术语、领域和翻译记忆相关参数，适合直接承接翻译任务。 它是专用翻译接口，不等于通用聊天模型的全部能力。 |
| [SakuraLLM](https://github.com/SakuraLLM/SakuraLLM)<br>开放权重／非商用限制 | 本地推理／兼容服务 | 面向日中轻小说和 Galgame，适合作为文学方向的专项备选。 语言和文体较专门；模型有非商用许可限制。 |
| **优先看 · [DeepL API](https://support.deepl.com/hc/en-us/articles/4405021321746-Use-a-glossary-with-DeepL-API)**<br>商业 API | 文本／文件／术语接口 | 可以复用成熟服务与术语约束，作为通用翻译或对照路线。 API 账户、语言对和文件能力另看；网页订阅不等于 API 权限。 |

初步关注：HY 作为本地／低成本翻译候选，Qwen-MT 作为云端专用候选；DeepL 可作另一条商用翻译路线，日语文学再考察 Sakura。

### 2.2 文本决策与自动调度

对应 F-33。此类组件根据文本样本辅助选择模型、流程与开关，不承担正文翻译，也不替代用户现有 harness。自动调度是用户可启用的工作方式，不是新增的敏感性判定系统。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看 · [Jev / TypeSafe System One](https://typesafe.ai/blog/introducing-system-one-models-and-jev)**<br>商业决策模型／API | [官方结构化决策接口](https://api.typesafe.ai/docs) | 提供选项、评分和是／否类决策，适合判断所需翻译档位、是否补建词库、是否审校。它输出决策而非译文；可用模型、流程选项和翻译适用性资料仍需由本项目提供。 |
| **优先看 · [Semantic Router（Aurelio）](https://github.com/aurelio-labs/semantic-router)**<br>开源语义路由组件 | Python／本地或云端编码器 | 通过示例与语义匹配选择预设路由，适合先把文本分配给若干可编辑的翻译配置，也有本地执行路线。不是现成的翻译质量评测器，复杂条件可搭配规则或模型判断。 |
| [RouteLLM](https://github.com/lm-sys/RouteLLM)<br>开源模型路由框架 | Python／兼容服务 | 已有强／弱模型选择、阈值校准与评估流程，适合比较成本和模型分配。主要解决模型路由，不自动决定整条翻译链及建库开关；现有路由结果需用本项目的语言和文本样本校准。 |
| [SetFit](https://github.com/huggingface/setfit)<br>开源少样本分类框架 | 本地训练／Python 推理 | 可用少量标注样本训练文本分类器，并选择多语言编码器；适合后续将常见文本到翻译配置的判断沉淀为小型本地模型。不是即插即用的 Jev 等价模型，需准备本项目类别及样本。 |

初步关注：希望先验证 Jev 类决策体验时比较 **Jev**；希望优先复用可本地运行的组件时比较 **Semantic Router**。RouteLLM 作为模型路由对照，SetFit 作为后续已有样本时的小模型路线。也可先使用已有通用模型做结构化选择，不强制引入新的模型或训练流程。

自动选择需要同时参考文本与任务背景，例如语言、文体、用途、已有词库覆盖情况及用户可用的模型配置。“不开启构建术语库”仍可使用已有词库；“出现专业词”也不意味着每次都要重建词库。长书宜用有代表性的多处样本，而非仅看首页。模型的真实擅长范围要来自配置或已有比较结果，不由决策模型凭型号名称猜测；抽样策略和评价方法留待后续讨论。

F-33 决定“采用哪些模型和步骤”，F-34 决定“何时加载和释放”。例如在允许的资源范围内，术语处理接近结束时预热已选翻译模型；本轮不需要本地审校时，就不加载审校模型。无需每次把所有候选全文翻译后再比较，也不要求每个段落重新做一次完整流程决策。

### 2.3 翻译工作流、文学处理与可选编排

对应 F-10～F-13、F-19、F-22。

这组既有可调用组件，也有完整软件。完整软件不一定能直接拆出后台 API，因而明确区分接入与流程参考。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看 · [DocuTranslate](https://github.com/xunbu/docutranslate)**<br>开源文档翻译项目 | SDK／API／可拆组件 | 文本和多种文档的翻译流程与接口较接近本项目需求。 保留版式能力另比较；不要让它与 PDF 路线重复执行同一正文翻译。 |
| **优先看 · [translation-agent](https://github.com/andrewyng/translation-agent)**<br>开源参考实现 | Python 步骤适配 | 已有初译、审校和修订的参考流程，适合单独复用后两步。 不是成熟 CAT 工作台；多轮调用不自动等于质量更好。 |
| [AiNiee](https://github.com/NEKOparapa/AiNiee)<br>开源翻译应用 | 工作流／代码适配 | 长文、游戏与小说翻译中的词表和上下文处理值得复用或借鉴。 独立后台调用方式需进一步确认，不把图形界面直接当 API。 |
| [LinguaGacha](https://github.com/neavo/LinguaGacha)<br>源码公开的翻译应用 | 工作流／代码适配 | 小说、游戏和字幕等文本任务的另一套完整流程候选。 现成功能可比较，集成边界和具体许可另行确认。 |
| **优先看 · [GalTransl](https://github.com/GalTransl/GalTransl)**<br>开源专项翻译工具 | 脚本／工程配置／译文交换 | 已有视觉小说项目词典、name-message 文本交换及与提取／回填工具配合的流程。重点复用文学工作流或已译工程；补丁仍依赖引擎工具，不让它与内核各自初译全文。 |
| [Ebook Translator（calibre 插件）](https://github.com/bookfere/Ebook-Translator-Calibre-Plugin)<br>开源电子书插件 | calibre 插件／代码适配 | 面向电子书、多引擎翻译与阅读输出，补充 EPUB 和书籍使用场景。 适合外部工具协同或部分复用，不假定它能直接充当统一服务端。 |
| [Dify](https://github.com/langgenius/dify)<br>源码公开＋商业服务 | 工作流 API | 适合可视化试验多模型翻译和审校流程。 可选而非基座依赖；具体部署和许可按采用方式确认。 |
| [LangGraph](https://github.com/langchain-ai/langgraph)<br>开源编排库 | 代码集成 | 精翻步骤与多模型流程变复杂时，可复用流程编排能力。 用户现有 harness 已能完成的编排不必再复制一套。 |

初步关注：通用文档优先看 DocuTranslate；精细审校看 translation-agent 的分步骤思路；小说方向把 AiNiee、LinguaGacha、GalTransl 与 Ebook Translator 都放入候选。

Dify、LangGraph 仅作为可选的翻译工作流编排组件，不另造一套必须使用的 harness。

### 2.4 术语管理、分类与候选发现

对应 F-14～F-19。

没有必要要求一个软件同时完成词库管理、自动分类、证据检索和正文翻译。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看 · [Terminologue](https://www.terminologue.org/docs/intro.en/)**<br>开源术语管理 | 编辑界面／导入导出 | 概念、多语言表达、审核与历史适合直接建立人工管理基础。 自动写入和复杂分类接入需再看接口，不预先声称一键串通。 |
| **优先看 · [VocBench 3 / Semantic Turkey](https://vocbench.uniroma2.it/doc/user/)**<br>开源词表平台 | Web API／RDF | 分类、关系、多语言概念管理较完整，适合跨领域词库。 后台较重；不必让完整管理平台随每次翻译常驻。 |
| [TemaTres](https://github.com/tematres/TemaTres-Vocabulary-Server)<br>开源词表服务器 | 数据服务／界面 | 分类树、叙词表与受控词表的另一条轻量化候选。 翻译专用字段与 LLM 建库仍需适配。 |
| [Skosmos](https://github.com/NatLibFi/Skosmos)<br>开源词表浏览器 | REST／浏览界面 | 现成的层级查看与查询发布层，便于访问已有词库。 主要用于浏览检索，不替代条目编辑和自动建库。 |
| [Annif](https://github.com/NatLibFi/Annif)<br>开源自动标引工具 | REST／CLI | 根据文本推荐已有主题，可用于文档或术语分类辅助。 不是双语术语翻译器；部分后端需要训练材料。 |
| [KeyBERT / YAKE](https://github.com/MaartenGr/KeyBERT)<br>开源提取组件 | Python 库 | 复用关键短语候选提取，减少从零编写提取算法。 关键词不是已确认专业术语，仍需结合上下文与已有库判断。 |

初步关注：先比较 Terminologue 的管理体验与 VocBench 的结构能力；Annif 是辅助分类候选。商业术语系统与 CAT 一并列在第 2.5 节。

### 2.5 精翻工作台与编辑组件

对应 F-20～F-22、F-26、F-39；现有编辑器和翻译记忆功能可优先复用。F-43 的多人协作列 P3，不因为候选中含有 TMS 平台就将其设为近期依赖。

### 2.6 词典与外部术语查证（F-40／P1）

**按用户修改稿，F-40 的当前优先级为 P1。**功能范围不变：接入真实可用的词典或术语来源，既供人工查证，也供建库和翻译流程按需参考。支持在线服务与本地数据两条路线，由用户选择；不要求先自行部署面向公众的词典服务器。

下面只做初筛，并区分词典内容、格式工具和在线接口。优先级给的是 F-40，不等于每个来源都要首批接入；具体语言、专业覆盖、许可和费用在选少数对象时再比较。

| 候选／性质 | 可接方式 | 简要分析 |
|---|---|---|
| **优先看（本地英汉） · [ECDICT](https://github.com/skywind3000/ECDICT)**<br>开源词典数据／工具 | CSV／SQLite／查询代码 | 已有英文与中文释义、词形信息和数据读取方式，可低成本验证本地词典进入翻译流程。主要是通用词汇，不当作微磁学等专业术语的最终标准。〔C78〕 |

初步关注：**后台复用先比较 manga-image-translator 与 manga-translator-ui；人工修订先看 BallonsTranslator；希望保持原图时看 mokuro；非日语与整卷使用体验用 Comic Translate 作对照。**不同选择共用同一作品词库和已接受译文，不重复做两套完整翻译。

建议输出同时考虑“可读成品”和“可继续编辑的结果”：前者是逐页译图、图片包／CBZ／PDF 或原图加译文显示；后者保存与图中位置对应的原文和译文，并可按工具支持交换工程或图层。CBZ／PDF 是本项目的可选打包目标，不要求每个候选都原生支持；可编辑也不等于首期承诺所有 PSD／其他工程格式无损往返。

[manga-translator-ui 的工作流说明](https://hgmzhn.github.io/manga-translator-ui/en/workflows/import-translation-and-render.html)和[维护者 CLI／HTTP 文档](https://github.com/hgmzhn/manga-translator-ui/blob/main/doc/CLI_USAGE.md)已有“导入译文再渲染”的路径；这是避免第二次正文翻译的优先复用点。不要把其默认“导出译文”流程误当作无模型调用的普通导出，具体模式应单独选择。

漫画的阅读顺序、竖横排、跨页对白、拟声词和嵌字空间，需要在选型和人工修订中考虑；普通短句可继续用文本模型，有需要时才加入图像上下文。图中文字只翻译一次，后续更换字体、调整气泡、重排或打包读取已有译文；若确实要改写某句，再进入原有精翻流程。抹字失败可保留原图、采用叠字或人工修补，不把自动修复视为总能恢复被文字遮挡的画面。

## 后续选型讨论

候选池不等于安装清单。按要解决的实际场景挑选少数工具，比较接入方式、使用体验、译文往返与部署代价；本次不展开协议字段或细粒度测试矩阵。

本地、联网、模型和词库共享由用户设置；自动调度只在用户启用的范围内工作。功能插件可按需要向 MCP 基座注册能力，不要求所有内部调用改为 MCP。

同一译文和可迁移词库仍是选择候选的主要关注点：连接现成翻译流程时，尽量复用已经完成的译文；不同输出、回填或重新排版不再单独初译。

词表结构可参考 [SKOS](https://www.w3.org/TR/skos-primer/)，物理主题可参考 [PhySH](https://physh.org/about)；它们不是现成多语言术语库。

本轮仅将用户修改后的需求优先级和范围同步到候选表，83 项能力描述与既有来源沿用 v0.5，未新增联网核查、部署或联调。字幕自动生成到翻译的后续意向暂不新增组件选型。DOCX、JSON 与旧资料包保持不变。
