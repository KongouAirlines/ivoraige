# 精翻项目综合保存与语义比较（规划引子）

关联 [#35 精翻](https://github.com/KongouAirlines/ivoraige/issues/35)、[#36 Git 协作](https://github.com/KongouAirlines/ivoraige/issues/36)、[#16 项目制](https://github.com/KongouAirlines/ivoraige/issues/16)及 [#106 的修订界面建议](https://github.com/KongouAirlines/ivoraige/pull/106#issuecomment-6943790443)。这里保存产品方向、需要联合设计的问题和后续验证场景，**到精翻阶段再细化并改造，不固定 schema、目录、存储引擎、Git 提交粒度或实现时间**。现有编辑恢复、文档导出和页面迁移不等待这一整套机制。

## 为什么不只增加一个历史列表

当前单元译文 Revision、accepted 与文档 ExportSnapshot 分别解决修订、采用和一次输出的冻结，不足以表达包含多文档、结构、原文、译文、项目资源的完整项目版本。源码参考基线 main `686dd324` 的 [修订写入/接受](https://github.com/KongouAirlines/ivoraige/blob/686dd3249d4d773eed38b1ca2888ca19bb565ef3/src/records.mjs#L716-L779)、[快照创建](https://github.com/KongouAirlines/ivoraige/blob/686dd3249d4d773eed38b1ca2888ca19bb565ef3/src/records.mjs#L796-L825)及解析逻辑。此处为静态核查，不是数据迁移已完成。

今后原文更新、拆段、合段、移动或资源替换后，仅保存旧 revisionId 不足以证明旧结构和来源仍可解释；应与历史文档结构、来源绑定及资源版本一并设计。近期 Git 式时间线只是视图，不能反过来限定精翻的数据模型。

## 三个层次共同设计

| 层次 | 目的与方向 | 需要区分的动作 |
| --- | --- | --- |
| 短时寄存 / 恢复 | 保存未完成编辑、临时草稿和必要工作状态，处理中断、误操作和崩溃；恢复承诺限定于已确认持久化内容 | 自动寄存不等于接受译文或保存正式版本，也不需要每个按键生成 Git commit；保留期限/清理策略待定 |
| 长期项目版本 | 以 Git 仓库为长期历史方向，保存可命名、比较、恢复的项目整体状态及必要结构关系；用户不必操作 Git 命令 | 保存版本与推送/共享分开，本地单人工作不要求远端仓库；具体提交时机、仓库粒度和协作方式精翻阶段评估 |
| 面向人的变更视图 | 结合稳定身份、结构操作关系和文本差异解释修改；Git diff 可作为基础材料，不是最终 UI 或唯一事实来源 | 结构变化、文字变化、接受状态变化及资源变化可组合呈现；自动推断须标明不确定性并保留可核对原始对照 |

短时寄存、项目版本、运行定义快照与导出快照彼此可关联，但不是同一种对象。长期版本不能依赖会被自动清理的寄存内容；保存版本也不自动启动任务、调用模型、导出或同步到团队。

## 项目综合保存及恢复边界

一个项目版本应能确定当时的成员文档与顺序、结构/来源版本、原文与译文、采用状态、项目配置及项目资源，而非只有正文文件。当前状态要可直接读取，不强制重放全部历史事件才能打开项目。

大原件、图片、附件和共享术语库可以评估项目内保存或确定版本的引用，但引用必须有可取回性与完整性保证；缺失资源应明确报告，不能声称完整恢复。凭据、机器私有路径和短暂运行状态不能混入可分享版本；资源权限仍需独立检查。

项目综合保存与局部查看/恢复不矛盾。恢复单文档或局部内容应说明范围与影响，不悄悄回滚其他项目共用的资源，也不改写历史快照。恢复倾向形成新的可追踪工作状态；共享引用还是项目隔离副本、采用状态如何跨项目作用等政策留待精翻设计。项目多文档版本需固定成员与引用的一致视图，不能随意逐个读取导致跨时刻混合；事务或一致性协议不在此指定。

## 将结构变化记录与正文变化对应

拟在项目格式中显式表示单元的稳定身份及新增、删除、移动、拆分、合并关系，并与具体文档/项目版本关联，而非一个不断覆盖的“最后修改”字段。单元身份不能只由位置、顺序或相同文字决定。

例如 A → B + C 表达拆分，A + B → C 表达合并；关系还需能对应来源/目标文本范围或等价锚点，才能说明字词到底改在哪里。一次操作同时拆分并改字很常见，应能组合解释，不强迫分为两个用户动作。具体范围编码、锚点、操作批次及结构记录是否需要完整事件日志均未决定。

语义比较的候选流程是：读取两个确定版本 → 核对稳定身份与明确结构关系 → 在对应范围比较字词 → 组合展示结构、正文、状态和资源变化。拆成两段并改词时，优先表达“拆分为两段”以及各处文字变化，而非只能显示整段删除、两整段新增。多次拆合移动的跨版本比较还要研究关系组合与歧义，不假定单步操作即可恢复完整历史。

外部编辑或缺少结构记录时，可尝试匹配，但推断不是事实；提供不确定标记、前后全文/原始差异和人工确认路径，不能按同文自动合并身份。语义摘要必须能展开真实变化，尤其区分源内容和派生输出，避免隐藏遗漏或把自动文本合并成功误认为翻译语义正确。

## 精翻阶段需要回答的问题

- 权威项目内容、数据库索引/缓存、Git 工作树与短时寄存的职责及一致性；避免多份可写真相互相覆盖。
- 稳定序列化、文件粒度、大附件存储、结构关系及版本引用；避免整份大 JSON 小改全重排，也不预先要求每段一文件。
- 单元身份/来源对应、原文更新和结构调整后的 accepted 适用性；历史导出依赖的结构/资源保留与回收。
- 自动寄存、保存版本、接受、导出、恢复和对外同步的不同语义、失败恢复与权限边界。
- 共享资源局部恢复、并发编辑、Git 冲突、外部修改、旧版本迁移和大文档性能；不假定 Git 能自动解决项目语义冲突。

后续最小验证应覆盖：拆分同时改字；合并/移动后跨版本比较；重复文字但不同单元；结构记录缺失的外部编辑；项目多文档一致保存；缺资源不伪报恢复成功；恢复一篇不回滚共享库；中断不破坏已保存版本；旧文档独立导出及冻结历史保持兼容。这些是精翻设计时细化的场景，不新增当前 UI 重绘的总前置或完成声明。
